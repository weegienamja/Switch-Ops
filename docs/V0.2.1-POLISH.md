# SwitchOps v0.2.1 — correctness and product-quality pass

v0.2 built a data model more sophisticated than the experience on top of it, and
one part of that model was wrong. v0.2.1 fixes the modelling error and closes the
gap between what SwitchOps knows and what it shows. No new subsystem, no AI, no
background services, and physical write execution stays disabled.

---

## 1. The topology correlation bug

### What it looked like

Against the real lab, the evidence map showed:

```
Uplink to Test Gateway 1     router   observed   Gi0/1
Uplink to Test Gateway 2     router   observed   Gi0/1
Uplink to Test Gateway 3     router   observed   Gi0/1
```

Three directly connected Test ISP routers. There is one.

### Root cause

`build_topology` iterated the MAC-table entries learned on each interface and
created a `NetworkDevice` per entry:

```python
for index, entry in enumerate(attached):
    device = NetworkDevice(
        name=device_name if len(attached) == 1 else f"{device_name} {index + 1}",
        source="observed",
        confidence="high",
        ...
    )
```

Two errors compound there:

1. **Cardinality.** A MAC learned *through* an interface is not a device attached
   *to* that interface. On an uplink or trunk, every address on the far side of
   the neighbour appears on that one port. The switch learns them because that is
   the direction traffic arrives from, not because they are plugged in.
2. **Identity.** The interface *description* was copied onto each node and marked
   `source="observed"`, `confidence="high"`. The description is a label the
   operator typed. It is evidence about what is *expected*, never about what was
   *discovered*.

### The fix

`build_topology` now enforces one hard invariant:

> **At most one endpoint device node is created per switch interface.**

Additional learned addresses become `learned_mac_count` on the interface, the
link and the endpoint — "N addresses are reachable through this link" — never
extra nodes. Identity is tracked separately from existence, so a name taken from
a description is labelled as such.

Supporting changes:

- **Stale MACs.** Addresses on a port whose operational state is down no longer
  manufacture an online device; entries age out on their own schedule.
- **Attribution.** A single learned address is attached to the endpoint. Several
  are not — picking one of five would be a guess, so `mac` stays `None`.
- **Node identity.** Endpoint ids derive from the interface when no single
  address can be attributed, so two ports with the same description cannot
  collide.
- **Interface role.** `classify_interface_role` marks an interface `uplink` or
  `access` from its description or a trunk VLAN. This drives layout and
  interpretation only; it never changes how many nodes are produced.

### Verified against the hardware

Both models were run over the *same* real observation from the physical
WS-C3560CG-8PC-S:

| | v0.2 | v0.2.1 |
| --- | --- | --- |
| Endpoint nodes | 7 | 5 |
| Nodes for Gi0/1 | 3 | 1 |
| Gi0/1 name | "Uplink to Test Gateway 1/2/3" | "Uplink to Test Gateway" |
| Addresses behind Gi0/1 | modelled as devices | `learnedMacCount: 3` |

Then re-confirmed through the packaged 0.2.1 release against the live switch.

## 2. Evidence model

| Level | Means | Produced by |
| --- | --- | --- |
| `direct` | The neighbour announced itself on the wire. | CDP neighbour on a linked interface |
| `observed-on-port` | Something is demonstrably attached — link up and addresses being learned — but SwitchOps cannot prove it is a single device rather than another switch. | learned MACs + oper up |
| `learned-behind` | An address reachable through the interface, possibly several hops away. | surplus MAC-table entries |
| `expected` | Only the interface description suggests this device. Nothing observed. | description on an idle port |
| `unknown` | Not enough evidence. | default |

`identitySource` records where a *name* came from: `cdp`, `interface-description`,
`mac-oui`, `switch-telemetry`, or `none`.

The two are deliberately independent. On Gi0/1 the **link** is high confidence
(it is certainly up and learning) while the **device identity** is medium at best
(the name is a description). The UI states both.

CDP is now collected during the dashboard sweep — one extra allowlisted
`show cdp neighbors detail` per refresh. It returns zero entries on the current
lab, which is correct and is not treated as a failure. It matters for the TEST-AP:
if the AP advertises itself, Gi0/4 upgrades from `expected` to `direct` with a
real name and platform instead of a description.

## 3. What each screen does now

| View | Job |
| --- | --- |
| Overview | Current health, and an honest record of how often you have looked. |
| Visual network | The lab as one picture, plus everything known about one port. |
| What changed | Structured transitions first; raw IOS behind Advanced. |
| Lab Guide | Beginner questions answered with the user's own hardware. Nothing else. |
| Change control | Learn → Plan → Review → (Apply, not available). |

### Visual network

The Catalyst front panel is the centre of the topology rather than a separate
card. Upstream devices sit above it, endpoints below, and a cable runs from each
device to the physical port it is plugged into. Cable geometry is measured from
the rendered DOM, so a device stays aligned with its real port at any width.

- solid cable — observed
- dashed cable — expected from a description only
- chip on the cable — "+N behind" where more addresses are reachable through it
- selected port highlights the port, the cable and the node together

Device art is inline React SVG. One drawing expresses observed / waiting /
no-link through `currentColor`, so no state needs a second asset and the map
issues no image requests.

### Observation history

SwitchOps has no background poller. A row exists because somebody pressed
refresh, so the panel says so, counts observations rather than "samples", draws
discrete markers below three observations, and places sparkline points by real
elapsed time above it — gaps read as gaps in observation, not flat readings.

## 4. Test connection

`POST /api/setup/test-connection`, read-only, serialized with all other device
access, session closed in a `finally`.

| Check | Proven by |
| --- | --- |
| Stored credentials available | credential store reports a configured backend |
| Host reachable on TCP 22 | TCP connect with a 4 s timeout |
| SSH session established | transport negotiated and opened |
| SSH host key matched | pin compared, or first key recorded |
| Authentication succeeded | the switch accepted the stored account |
| Cisco IOS detected | `show version` parsed |
| Read-only operations available | `show interfaces status` returned parseable rows |

It deliberately does **not** claim Internet reachability, privilege level, switch
health, or anything about the wider network, and the UI says so.

Failure detail is classified into a fixed vocabulary (`host_key_changed`,
`authentication_failed`, `timed_out`, `ssh_negotiation_failed`,
`connection_failed`, `credentials_missing`, `host_unreachable`,
`unsupported_platform`, `read_ops_unavailable`) rather than echoed. A
server-side exception string can therefore never carry a username, path or
secret into an API response — asserted by
`test_no_failure_detail_echoes_the_underlying_exception`.

A changed host key is reported as a blocked step with the later checks skipped,
not as a generic error.

## 5. Security boundaries (unchanged)

All v0.2 boundaries hold:

- backend binds `127.0.0.1` only; CORS limited to localhost and `tauri://localhost`
- mutation origin check on every POST/DELETE
- device access serialized behind one process-wide lock, including the new test
- SSH host key pinned on first use; changes fail closed
- credentials in Windows Credential Manager, never in source, logs or responses
- no raw CLI endpoint; every command resolves through the symbolic registry
- `Gi0/1`, `Gi0/2`, `Vlan1` refused at the registry regardless of write mode
- write actions disabled by default, and no apply endpoint exists for plans
- API docs disabled by default
- legacy SSH algorithms applied in-process only

`GET /api/system/info` was added and returns only non-secret local configuration
(bind address, retention, whether a host key is pinned, storage directories).

---

## 6. Deliberately not done

- No AI, model, or vector store. Deterministic explanations do this job.
- No traffic-rate collection. It cannot be done from existing aggregate data
  without polling this IOS release harder than is justified, so it stays deferred.
- No background service or poller.
- No Meraki cloud dependency. The TEST-AP has not been physically connected, so
  nothing claims it has.
- No new runtime dependency in the backend, frontend or desktop shell.

## 7. Next: the TEST-AP

The model is ready for it. Before the AP is attached, Gi0/4 reads *expected /
waiting*, `learnedMacCount: 0`, dashed cable — pinned by
`test_physical_lab_expected_ap_is_ready_for_the_mr44_transition`. After
attachment SwitchOps should observe the link, PoE draw, negotiated speed and a
learned address, and record link-established, PoE-started and device-appeared
events. If the AP advertises CDP the node upgrades to `direct` with its own name;
if it does not, it stays `observed-on-port` with the description-derived identity
and says so. Both outcomes are correct behaviour, and neither fabricates an
TEST-AP identity the switch did not report.
