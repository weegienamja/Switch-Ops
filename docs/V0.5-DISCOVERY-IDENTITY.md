# SwitchOps v0.5 — Discovery & Identity

## Purpose

The v0.5 discovery engine answers five separate questions:

1. Does something exist?
2. Where was it observed, and what is its relationship to that interface?
3. What identity attributes are actually supported?
4. How strong and how fresh is the supporting evidence?
5. Does the observation agree with intent and history?

No source is allowed to answer a question it cannot prove. In particular, an
interface description is operator intent and never an observation of the named
device.

## Knowledge and claim axes

Every record retains its knowledge class:

- `observed` — current device telemetry;
- `expected` — interface description, local user intent, or accepted plan;
- `inferred` — a conclusion supported but not directly proven by evidence;
- `historical` — previously observed and no longer current.

Existence, identity, attachment, relationship, and role are independent claim
flags. A current link plus a learned MAC can strongly establish endpoint
existence while leaving identity unknown.

## Evidence sources

| Type | What it can support | Important limitation |
| --- | --- | --- |
| `INTERFACE_LINK` | physical link/existence | no identity |
| `INTERFACE_DESCRIPTION` | intended label/category/role | no existence or identity |
| `CDP_NEIGHBOR`, `LLDP_NEIGHBOR` | direct relationship and advertised identity | only fields the neighbour advertises |
| `MAC_LEARNED` | L2 existence and reachability through a port | not necessarily direct attachment |
| `ARP_ENTRY` | IP-to-MAC correlation and path | not direct attachment or a hostname |
| `LOCAL_HOST_MAC` | conservative identity of the PC running SwitchOps | only when one active non-randomised adapter uniquely matches one connected access port |
| `OUI_VENDOR` | vendor hint | no model, hostname, category, or role; invalid for local/multicast addresses |
| `USER_INTENT`, `ACCEPTED_PLAN` | explicit intended topology | not an observation |
| `PRIOR_OBSERVATION` | historical continuity | not current truth |

The OUI registry is bundled by the pinned `netaddr` dependency. Lookup is local
and requires no cloud service. Registry data can become outdated between
dependency updates; unknown assignments degrade cleanly to no vendor hint.

## Relationships

- `direct-neighbour` — a CDP/LLDP neighbour announced itself on the interface;
- `attached-endpoint` — current link evidence establishes something at the
  edge, without necessarily identifying it;
- `learned-behind` — an address is reachable through the interface and may be
  several hops behind an uplink, AP, bridge, hypervisor, or downstream switch;
- `gateway-path` — ARP plus MAC learning puts the default gateway in this
  direction without identifying the physical neighbour;
- `expected-neighbour` — intent only.

Multiple learned addresses never create multiple directly attached cards.

## Confidence and conflict

Confidence is categorical: `unknown`, `low`, `medium`, `high`, or `confirmed`.
Existence and identity have separate confidence values. Central backend rules
assign confidence; frontend components only present it.

Local-host correlation can confirm identity. Current CDP/LLDP normally provides
high identity confidence. OUI alone is low; OUI plus a single MAC/ARP path can
be medium for partial vendor/IP enrichment but still does not produce a device
name. Conflicting observed sources are retained as `EvidenceConflict` records,
lower identity confidence, and make reconciliation uncertain instead of
silently selecting whichever source ran last.

Expected identity disagreeing with a reliable current announced identity is
topology drift. Conflict among current observations is uncertainty. Health and
topology reconciliation remain independent.

## Freshness and revocation

Evidence is `current`, `aging`, `stale`, or `historical`. Current windows exceed
normal collector intervals, so one skipped or failed poll does not delete a
topology. Reconnecting and offline sessions can make facts stale but cannot by
themselves prove disappearance. A successful observation that no longer
contains the entity revokes its current evidence and moves the entity into
history.

Fast live interface overlays set a disconnected node to aging rather than
instantly deleting it. The next complete discovery observation either restores
it to current or revokes it.

## Persistence and API

`discovery-history.sqlite` uses `PRAGMA user_version = 1` and stores stable
entities, current evidence, and timestamped evidence observations. It is local
private application data. The existing `topology-intent.sqlite` is migrated in
place from the unversioned v0.4.1 schema to version 1 without dropping rows.

The typed `TopologyModel` remains the authoritative dashboard API object and
now includes evidence, port expectations, historical devices, and an evidence
model version. Deep observations also publish a `topology_state` SSE event.
The frontend never rebuilds identity from labels or raw tables.

## UI semantics

- **Observed** is the default and gives full nodes only to current existence
  evidence. Inactive descriptions appear as compact port expectations.
- **Reconciled** overlays aligned, drift, expected-not-observed, unexpected,
  uncertain, and not-applicable results.
- **Expected** emphasizes intent while continuing to label it as expected only.

The port inspector shows evidence type, provenance, strength, freshness,
existence confidence, identity confidence, last seen, and conflicts.

## Known limits

- CDP/LLDP absence does not mean a neighbour is absent; many real devices do
  not advertise useful identity.
- A MAC table and ARP cache are reachability data, not a physical-cabling map.
- OUI registration can be virtualized, reassigned, spoofed, or randomized.
- v0.5 does not add DHCP, DNS, SNMP polling, Meraki API, active probes, or cloud
  enrichment. The formal evidence model leaves those as future sources.
- Formally verified hardware remains `WS-C3560CG-8PC-S` with IOS
  `12.2(55)EX2`; other Catalyst models are not claimed as validated.
