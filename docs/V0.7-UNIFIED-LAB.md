# v0.7 Unified Lab

## Purpose

Unified Lab answers a narrower question than either provider UI:

> Which entities and relationships are supported by Catalyst, which by Meraki,
> which by both, and where do those sources disagree?

It does not copy the Meraki Dashboard and it does not expand SwitchOps write
authority.

```text
Catalyst IOS evidence ---\
                          +--> normalized claims --> reconciliation
Meraki Dashboard evidence /
```

## Provider-neutral contracts

Collectors return only:

- provider-local entities;
- protected identifiers;
- compact typed claims;
- structured provenance and collection completeness;
- freshness and source health.

Raw IOS command output and raw Meraki responses are outside this contract.
Every claim names one provider and source kind, an opaque source-object
reference, observation/collection times, scope, strength, and completeness.

Evidence strength has three levels:

- **strong**: an exact device serial or globally administered device/chassis
  hardware MAC;
- **supporting**: a management address, direct adjacency, or reciprocal
  LLDP/CDP observation;
- **weak**: a name, model, or description hint.

Locally administered/randomized MACs never become durable identity keys.

## Deterministic identity

Identity resolution uses no fuzzy threshold and no last-writer-wins rule.

1. An exact unique strong identifier can confirm a cross-provider identity.
2. Supporting or weak agreement creates a visible candidate only.
3. A comparable strong disagreement on an otherwise plausible pair creates a
   conflict and merges nothing.
4. Unrelated serialized devices do not create conflicts merely because their
   identifiers differ.
5. The operator can confirm or reject an ambiguous candidate locally. The UI
   cannot override a strong conflict.

Confirmed records form one unified entity. Every field still reconciles
independently, so an identity can be agreed while its name or availability is
in conflict.

## Cross-provider states

- `AGREED`: multiple providers currently report the same value.
- `PROVIDER_ONLY`: exactly one provider reports the value.
- `STALE`: only stale or historical evidence remains.
- `AMBIGUOUS`: a provider or identity candidate has multiple plausible values.
- `CONFLICT`: current providers disagree, or strong identity evidence conflicts.
- `UNKNOWN`: no provider supplies this claim.

These states apply separately to identity, attachment, relationship,
availability, name, model, VLAN, and port context.

## Meraki read boundary

The API key is stored only in Windows Credential Manager under the dedicated
`switchops-meraki` service. There is no file/environment fallback. Organization
and network IDs/names are stored in a private local selection file.

The client can perform only named `GET` operations:

- organizations and organization networks;
- assigned organization devices and current device availabilities;
- device LLDP/CDP;
- organization MX/Z uplink status and network MX ports;
- MS switch-port status for MS devices;
- recent network clients.

Operation paths, path values, and query keys are validated. Pagination follows
only `https://api.meraki.com/api/v1/...` links with allowlisted query keys.
`429 Retry-After`, transient server failures, transport failures, and later-page
failures are bounded and reported as source health or partial evidence. The
client exposes no method that accepts an arbitrary URL or HTTP verb.

The implementation follows the current Cisco Meraki Dashboard API v1 operation
contracts and bracket form for array query parameters:

- <https://developer.cisco.com/meraki/api-v1/get-organization-devices/>
- <https://developer.cisco.com/meraki/api-v1/get-organization-devices-availabilities/>
- <https://developer.cisco.com/meraki/api-v1/get-device-lldp-cdp/>
- <https://developer.cisco.com/meraki/api-v1/get-organization-appliance-uplink-statuses/>
- <https://developer.cisco.com/meraki/api-v1/get-network-clients/>

## Privacy and persistence

Device serials, global hardware MACs, management addresses, and ephemeral client
addresses are HMAC-protected with a random per-install key before normalized
state is persisted. Protected values allow equality tests only within that
SwitchOps installation.

Recent clients are represented as short-lived pseudonymous attachment
observations. Raw client MAC/IP addresses, usernames, descriptions, usage,
device predictions, and SSID names are not stored or returned. Provider payloads
are discarded as soon as the useful fields are normalized.

The private `unified-lab.sqlite` database stores only normalized provider
snapshots, source health, and local identity decisions. Synthetic fixtures live
under backend tests and are excluded from packaged builds.

## UI and control boundary

Unified Inventory displays provider badges, source health, freshness,
per-attribute states, conflicts, candidates, and claim provenance. Visual
Network retains the Catalyst-derived port geometry and adds a labelled Meraki
overlay instead of pretending Meraki evidence came from IOS.

Change Control remains backed by the existing Catalyst evidence, local interface
policy, process lock, preflight, and bounded IOS executor. No Unified Lab or
Meraki claim can make an interface operable, unlock writes, submit IOS CLI, or
write to the Meraki Dashboard.
