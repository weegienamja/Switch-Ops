# v0.8 Lab Assurance

## Purpose

Lab Assurance answers:

> What does the current evidence prove about this lab, what depends on what,
> and what is likely to happen if a component or service path degrades?

It is an initially read-only analysis layer. It does not add IOS writes, widen
the Meraki boundary, or bypass Change Assurance.

```text
allowlisted IOS/IOS-XE observations
        |
        v
capabilities + normalized claims
        |
        v
physical/logical lab graph
        |
        +--> findings
        +--> failure scenarios
        +--> path explanations
        +--> bounded service probes
```

## Capability contract

Every capability is one of:

- `SUPPORTED`: current command output or explicit running configuration proves
  the feature exists on this device;
- `UNSUPPORTED`: IOS explicitly reports that the feature itself is unsupported;
- `UNKNOWN`: the available evidence cannot decide.

An invalid, ambiguous, incomplete, or unavailable command form is observation
evidence about that command only. It leaves the capability `UNKNOWN`, as do
authorization failure, insufficient privilege, collection failure, and parser
failure. This avoids treating syntax differences between IOS releases as a
platform capability verdict.

`configured` and `observed` are separate nullable fields. A device being Cisco,
Catalyst, IOS, or IOS-XE is never sufficient support evidence.

The initial catalog covers Layer 2 switching, Layer 3 routing, VLANs, trunks,
STP, EtherChannel, PoE, CDP/LLDP, routing tables/neighbours, first-hop
redundancy, VRFs, interface/error telemetry, DHCP snooping, DAI, AAA, IP SLA,
BFD, BGP EVPN, VXLAN/NVE, Segment Routing MPLS, and SRv6 when the fixed
read-only evidence is available. Simple devices will correctly report many of
these as unknown or unsupported.

## Multiple IOS/IOS-XE devices

The existing Catalyst remains the primary serialized session. Additional
devices are deliberately configured in the Lab Assurance Capabilities view and
collected sequentially through the same fixed command registry.

Secondary-device credentials have no file or environment fallback:

- a random `lab-*` ID is written to `lab-device-registry.json`;
- label, target, username, password, enable secret, and platform live together
  in Windows Credential Manager;
- deleting the device removes its keyring entry;
- API responses never contain the target, username, password, or enable secret.

Each session is closed after its bounded read-only collection. A failed device
produces a failed/partial source with unknown results; other device evidence
remains usable.

## Graph and identity rules

Nodes include independently collected devices and privacy-minimized discovered
infrastructure/endpoints. Edges retain kind, hop state, categorical confidence,
reciprocity, interface context, explanation, and evidence IDs.

- CDP/LLDP is direct-neighbour evidence.
- Exact unique hostnames can reconcile a discovered neighbour with another
  independently collected device. Fuzzy names do not.
- Reciprocal port-aware discovery yields confirmed confidence.
- One-sided direct discovery remains high confidence.
- MAC learning says an identity is reachable behind a port. It is `INFERRED`
  and is never called a direct physical cable.
- ARP plus MAC can place a default-gateway relationship on a forwarding port,
  but that relationship remains inferred.
- Routing adjacencies are logical relationships, distinct from physical links.
- Port-channel membership is a membership edge, not another neighbour.

Clear MAC, ARP, and routing peer values are used only during in-memory
normalization. Emitted endpoint/gateway/peer IDs are opaque hashes.

## Assurance findings

There is no numerical health or design score. Each finding has category,
severity, evidence confidence, affected IDs, evidence references, consequence,
and a suggested next check.

The current engine checks observable forms of:

- missing/single observed infrastructure paths;
- gateway and uplink dependency;
- unhealthy EtherChannel members;
- STP root placement;
- reciprocal access/trunk and native-VLAN inconsistency;
- unused administratively active ports;
- explicit BPDU Guard and port-security/802.1X coverage on access ports;
- DHCP snooping, DAI, and AAA evidence;
- PoE reserve below 20 percent;
- interface error counters;
- IOS HTTP/HTTPS management exposure;
- capability and source-evidence gaps.

Allowed-VLAN and capacity analysis is conservative. A mismatch is asserted only
when both ends of a reciprocal discovered link were independently collected.
Unknown peer policy remains unknown.

## Failures and paths

Failure scenarios remove an observed graph edge or node and recompute
reachability from the primary SwitchOps device. Endpoint-facing interface
scenarios identify only inferred attachment groups whose current forwarding
path uses that interface; they do not promote the port to an uplink. Results
state categorical confidence and separately explain possible control-path
impact. This is a simulation over current evidence, not a claim that a routing
protocol will or will not reconverge.

Path Explorer uses:

- `PROVEN`
- `INFERRED`
- `EXPECTED`
- `AMBIGUOUS`
- `UNKNOWN`

It never fills a missing hop because it looks obvious. An unconnected target is
returned as an explicit unknown path.

## Performance boundary

The local probe endpoint accepts only a syntactically valid IP address or DNS
hostname plus an operator label. It invokes fixed argument arrays with
`shell=False`:

- 1-5 ping requests with bounded per-reply and process timeouts;
- a numeric, maximum-12-hop route trace with a bounded timeout.

It reports `HEALTHY`, `DEGRADED`, `UNREACHABLE`, or
`INSUFFICIENT_EVIDENCE`, along with replies, loss, average latency, simple
jitter range, and route-change state when two parseable traces exist. Raw route
addresses and the clear target are not retained in the Lab Assurance state.

Link state is deliberately not promoted to service health.

## Logical network boundary

Logical networks project VLAN inventory, access members, trunks, SVIs/gateway
nodes, and VRF context where observed. VLAN separation proves a broadcast-domain
boundary, not security policy. The initial isolation state is therefore
`POLICY_UNKNOWN`; a future policy collector must supply enforcement evidence
before SwitchOps can claim isolation.

## Local API and CLI

Stable read endpoints:

- `GET /api/lab-assurance/state`
- `GET /api/lab-assurance/capabilities`
- `GET /api/lab-assurance/graph`
- `GET /api/lab-assurance/paths`
- `GET /api/lab-assurance/failures`
- `GET /api/lab-assurance/findings`
- `GET /api/lab-assurance/performance`

Bounded actions:

- `POST /api/lab-assurance/refresh`
- `POST /api/lab-assurance/performance/probe`
- typed add/remove endpoints for explicit secondary-device configuration

There is no raw command endpoint. The thin local CLI calls the loopback API,
replaces local display/target labels with their opaque IDs or tokens, and
prints privacy-safe JSON:

```text
switchops analyze [--refresh]
switchops paths [--from-node ID] [--to-node ID]
switchops failures
switchops capabilities
switchops performance
```

## Current limitations

- Analysis quality is bounded by command support, account privilege, collection
  completeness, and discovery configuration.
- A graph consequence does not prove application-level failover behavior.
- Route tracing can be filtered or incomplete and is not persisted as raw hops.
- No v0.8 operation configures IP SLA, discovery, routing, STP, EtherChannel,
  VLANs, security features, or probes on a switch.
- Meraki evidence remains in the v0.7 provider-neutral reconciliation layer;
  it does not grant IOS write authority or bypass the outstanding live-Meraki
  validation dependency.
